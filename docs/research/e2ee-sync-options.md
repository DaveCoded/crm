# End-to-end encrypted, local-first sync options

Research date: 30 September 2026. Scope: a personal CRM in this Vite+ repository, with a Tauri macOS app and Android app, offline edits on either device, asynchronous sync through an online relay, and a relay that cannot read relationship content. This is a technology assessment, not an architecture decision.

## Short answer

End-to-end encryption (E2EE) is feasible. A durable relay can store encrypted updates while the two devices connect at different times; each device needs to connect eventually, but they need not be online together. Automerge documents this asynchronous pattern for its sync server and offline clients. Its public community server is for prototypes, without reliability or data-safety guarantees. [Automerge network sync](https://automerge.org/docs/tutorial/network-sync/)

**Evolu 8 is the closest integrated candidate identified so far:** its documentation describes encrypted local SQLite, encrypted CRDT synchronization, mnemonic recovery, and a self-hostable relay. It is not yet verified in this repo or in Tauri Android, and the documented TypeScript requirement conflicts with this repo. [Evolu local-first guide](https://www.evolu.dev/docs/local-first), [Evolu privacy](https://www.evolu.dev/docs/privacy), [Evolu relay](https://www.evolu.dev/docs/relay)

There is **no demonstrated turnkey, production-ready combination** in the sources reviewed that simultaneously gives this app CRDT sync, E2EE, relay storage, macOS/Android support, and user-friendly recovery. The practical choice is to validate Evolu 8 first, then consider the alpha Keyhive integration or a custom encrypted-update layer if Evolu does not pass the project-specific gates. **Yjs plus Web Crypto supplies stable building blocks, not a stable turnkey E2EE sync stack: the security protocol and relay would be ours to design and maintain.** That assessment is an inference from the options below, not a vendor claim. The user has ruled out Classic Jazz.

**Relay hosting:** Evolu offers relay source and Docker files for self-hosting, permits multiple relays, and offers `free.evoluhq.com` **for testing only**, with no production hosting service from Evolu. Automerge also documents self-hosting a durable sync server and treats its community server as prototype-only. ARK's guide names hosted server identities and explains how to use a custom server identity; it does not promise that those hosted endpoints are a durable production service for this app. The Yjs encrypted-update route can use a small self-hosted service or a hosted storage/backend service **only if** it accepts and returns opaque blobs without decrypting them. That last point is an architecture requirement, not a feature claim for a particular provider. [Evolu relay](https://www.evolu.dev/docs/relay), [Automerge network sync](https://automerge.org/docs/tutorial/network-sync/), [ARK guide](https://automerge.org/docs/keyhive/ark-api-guide/)

## Evolu 8 adoption checks

Evolu 8 has a real integrated E2EE model, rather than only a storage-encryption plugin: its privacy docs state that local SQLite and outgoing data are encrypted, and that a relay cannot read content. The relay still sees an OwnerId, timestamps, ciphertext lengths despite padding, and IP addresses. Treat privacy language about traffic-analysis protection as a stated design goal rather than a guarantee that timing and all metadata disappear. [Evolu privacy](https://www.evolu.dev/docs/privacy)

The current getting-started guide requires **TypeScript 7 or newer** and `exactOptionalPropertyTypes`. This repo currently pins `typescript` to `~6.0.2` in `package.json` and does not enable that compiler option in `tsconfig.json`. Adoption therefore requires an explicit compiler upgrade and compatibility check with Vite+ before an Evolu implementation. The Evolu repository shows 8.x package releases, but release numbers alone do not prove this particular platform combination is stable. [Evolu guide](https://www.evolu.dev/docs/local-first), [Evolu releases](https://github.com/evoluhq/evolu/releases)

The Evolu guide documents browser/React web and React Native setup, and the FAQ describes browser OPFS SQLite. It does not document Tauri macOS/Android or confirm that its web dependencies work inside Android WebView. Tauri uses the device's system Android WebView, so a physical-device spike must verify Evolu's SQLite persistence, worker/runtime features, sync after offline edits, and app restart. This absence of official Tauri guidance is a research finding, not proof of incompatibility. [Evolu guide](https://www.evolu.dev/docs/local-first), [Evolu FAQ](https://www.evolu.dev/docs/faq), [Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/)

For recovery, Evolu can derive an AppOwner from a validated mnemonic and reconnect to relays holding its data. The app must securely persist the original owner secret, present/save the mnemonic, manage owner switching, and restore with the same app name; rows in `_`-prefixed local-only tables cannot be recovered from a relay. In Evolu 8, `deleteDatabase` and `deleteOwner` are declared but currently throw, so data purge cannot be assumed. Evolu 8 also does not yet migrate Evolu 7 databases. These are material maturity constraints for a product handling sensitive relationship data. [Evolu guide](https://www.evolu.dev/docs/local-first), [Evolu Owner API](https://www.evolu.dev/docs/api-reference/common/local-first/Owner)

## Why encryption placement matters

Local database encryption does **not** by itself prove E2EE. RxDB's encryption plugin encrypts selected fields in its **storage** wrapper and decrypts them when a document is read. Its own docs describe it as protection for data at rest on a device, while its replication interface sends documents to a backend. Consequently, one must inspect or explicitly encrypt the replication payload before claiming that an RxDB server cannot read it. [RxDB encryption](https://rxdb.info/encryption.html), [RxDB replication](https://rxdb.info/replication.html). Likewise, Automerge's ordinary public sync server is not presented as a secure production service; Keyhive is the separate encryption layer. [Automerge network sync](https://automerge.org/docs/tutorial/network-sync/), [ARK guide](https://automerge.org/docs/keyhive/ark-api-guide/)

For the Yjs route, encrypt **each incremental update** with authenticated encryption and a fresh, unique nonce; the server must never see an unencrypted Yjs update or a decryption key. Yjs can apply updates in any order and more than once, so an append-only relay can keep all updates until clients compact them. The relay cannot run Yjs state-vector/diff/merge operations on ciphertext; those operations interpret update bytes, so compaction and efficient differential sync need a client-side design. This is an inference from the Yjs update API and AES-GCM requirements. [Yjs updates](https://docs.yjs.dev/api/document-updates), [W3C Web Crypto AES-GCM parameters](https://www.w3.org/TR/webcrypto/#aes-gcm)

E2EE still leaves metadata visible to a relay: account or vault identifier, upload times, approximate sizes, number of updates, and network information. Protecting content does not make the entire usage pattern invisible. This is a consequence of the proposed opaque-relay design. A malicious or broken relay could also omit old updates or replay stale ciphertext; authenticated encryption detects alteration but does not on its own prove the relay sent the complete/latest history. Client tracking of seen update IDs or signed/checkpointed heads should be part of the prototype. This is a protocol design inference.

## Keys and adding the second device

For a single user, a randomly generated **vault key** shared only between authorized devices is simpler than multi-user document grants. The key needs an explicit onboarding path (for example, transfer from an unlocked first device via a verified pairing flow) and a recovery path if both devices are lost. A recovery phrase or passphrase-wrapped export could provide the latter, but its usability and threat model need design. Tauri's Stronghold plugin supports macOS and Android and can store local secrets, but it does not itself distribute or recover the vault key. [Tauri Stronghold](https://v2.tauri.app/plugin/stronghold/), [Stronghold API](https://v2.tauri.app/reference/javascript/stronghold/)

Keyhive handles member grants and rotations, but its guide says there is currently **no key backup or recovery mechanism** and that clearing its storage destroys the identity. That is a substantial product risk for a personal CRM, even if alpha is acceptable for a learning prototype. Its guide also requires the actual relay identity to match the configured server identity. [ARK guide](https://automerge.org/docs/keyhive/ark-api-guide/)

## Tauri and reminder implications

Tauri supports desktop and mobile targets, including macOS and Android. Its notification plugin lists both platforms, with scheduling available on mobile; the Android reminder can therefore be scheduled from locally decrypted data rather than requiring the relay to know contact names or due dates. This should be verified on a physical Android device for app-closed behavior and permission handling. [Tauri targets](https://tauri.app/start/), [Tauri notifications](https://tauri.app/plugin/notification/), [notification API](https://tauri.app/reference/javascript/notification/)

For local data, Yjs documents its `y-indexeddb` persistence provider; Tauri uses system WebViews (Android WebView on Android). The combination is plausible, **but unverified on Tauri Android**; persistence across app upgrades, WebView data clearing, and notification scheduling are prototype gates on physical devices. [Yjs offline support](https://docs.yjs.dev/getting-started/allowing-offline-editing), [Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/)

Yjs's documented `y-indexeddb` provider persists the Yjs document locally; the encrypted-update relay design alone does **not** encrypt that local copy. If local at-rest encryption is required, add and test a separate encrypted persistence layer rather than assuming E2EE transport provides it. [Yjs offline support](https://docs.yjs.dev/getting-started/allowing-offline-editing), [RxDB's IndexedDB encryption explanation](https://rxdb.info/articles/indexeddb/indexeddb-encryption.html)

## Recommendation for the next decision

Keep **E2EE, local encryption at rest, and recovery after loss of both devices as release gates**. **Spike Evolu 8 first** because it integrates the desired CRDT, E2EE, local database, recovery primitive, and relay. The spike must start with the TypeScript 7/Vite+ upgrade and then prove Tauri macOS and physical Android WebView persistence, offline concurrent edits, delayed cross-network sync, mnemonic restore after reinstall, self-hosted relay operation, and Android app-closed reminders. If those gates fail or its migration/purge limitations are unacceptable, compare ARK under the same tests or use encrypted Yjs updates with an opaque relay. The Yjs route has mature primitives but would make us responsible for the security protocol and relay; plain encrypted records remain a simpler non-CRDT fallback. CRDTs are a preference, not a hard requirement. Classic Jazz is excluded. [Evolu guide](https://www.evolu.dev/docs/local-first), [Evolu relay](https://www.evolu.dev/docs/relay), [Evolu privacy](https://www.evolu.dev/docs/privacy)

Before committing, decide what relay metadata leakage (contact/update counts and timing) is acceptable, and test the recovery and local encryption requirements on both devices.
